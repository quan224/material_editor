# F02 扩展调研笔记 — GPU Profiling（生产级做法 + 坑）

> 补足参考实现（per-pass timestamp + 三缓冲 + Qt）之外的生产级知识。

## 关键发现（容易踩的雷 + 升级点）

### 1. TIMESTAMP query 的正确姿势（多数人踩过）
- TIMESTAMP 是**唯一只调 EndQuery**（不需 BeginQuery）的类型；Begin 一个 timestamp query 会报错。
- 取数只能 `ResolveQueryData`：目标 buffer 必须 `COPY_DEST`，`AlignedDestinationBufferOffset` **必须 8B 倍数**。
- ⚠️ **resolve 一个未 EndQuery 完成或未初始化的 query = 未定义行为，可能 page fault / device removal**（debug layer 新版才报，老版是隐藏雷）。
- ms 计算**用 double**：`(double)(end-begin)/freq*1000`（官方建议，整数除法低频 GPU 误差明显）。
- "N 帧延迟"不是 bug，是异步管线天然结果——CL 执行完 + fence signal 才能 Map 读。
- 来源：https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing ｜ https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-resolvequerydata

### 2. Pipeline Statistics query（解释"为什么慢"）
- `D3D12_QUERY_TYPE_PIPELINE_STATISTICS`：每个 query resolve 写一个 88B 结构（11 个 UINT64）。**只在 Direct command list 支持**（compute/copy 不行）。
- 关键字段：`IAVertices/IAPrimitives`（提交量）、`CPrimitives`（clip 输出，和 IA 差=被裁剪数）、`PSInvocations`（实际着色像素=overdraw 指标）、`CSInvocations`。
- Mesh shader 要用 `PIPELINE_STATISTICS1`（多 MSInvocations/MSPrimitives），且有些驱动支持 MS 但不支持它的 stats。
- 价值：timestamp 说"多快"，pipeline stats 说"为什么"——PSInvocations 暴涨=overdraw 问题。
- 来源：https://microsoft.github.io/DirectX-Specs/d3d/CountersAndQueries.html

### 3. 跨命令列表/跨队列计时（静默错误源）
- Timestamp 频率是 **per-queue** 查的（`ID3D12CommandQueue::GetTimestampFrequency`），DIRECT/COMPUTE 总支持，COPY 可选。
- ⚠️ **不同队列频率可能不同**，跨队列直接相减算时间差**不合法**。
- D3D12 没有 `TIMESTAMP_DISJOINT` 了：**同一 CL 内两个 timestamp 总可比较**；**跨 CL 只有 `SetStablePowerState(TRUE)` 后才可靠**。
- ⚠️ `SetStablePowerState` **仅开发期**（会锁 GPU 时钟，release 绝不能用）。
- 频率不随时钟变，但低负载时 GPU 降频会"看起来更慢"——别误判。
- 来源：https://learn.microsoft.com/en-us/windows/win32/direct3d12/queries

### 4. PIX 集成（双轨：自研 profiler + PIX 事后深挖）
- `PIXBeginEvent/EndEvent` 标区间，`PIXSetMarker` 标时间点；GPU 重载传 command list。
- 实现：**不在应用进程 sprintf**，参数打包成 blob 由 PIX 端解码。
- **Timing capture ≠ GPU capture**：前者 ETW 长时段采集（需管理员权限），可程序化 `PIXBeginCapture(PIX_CAPTURE_TIMING,...)`。
- ⚠️ **用 DLL 不要静态链接** WinPixEventRuntime（多模块各自静态链接会 ETW 冲突）。
- 来源：https://devblogs.microsoft.com/pix/programmatic-timing-captures-now-available/ ｜ https://github.com/microsoft/PixEvents

### 5. 业级 profiler 架构（Tracy 的经验）
- 每个 queue 一个 context，ring query heap + 单调 NextQueryId，每帧 `GetClockCalibration(&gpuTick,&cpuTick)` 采样**把 GPU tick 线性映射到 CPU QPC 域** → CPU/GPU timeline 对齐（Tracy/PIX/RenderDoc 共用思路）。
- ⚠️ Tracy issue #227：GPU timer 读数**本身不可靠**，必须解析阶段**检测并丢弃异常 timestamp**（end<begin 或超阈值），否则 UI 闪烁。
- ⚠️ Tracy 的 `NextQueryId` **非线程安全**——多线程录制 CL 要每线程独立 query 区段/锁。
- 来源：https://github.com/wolfpld/tracy/issues/227 ｜ https://www.reedbeta.com/blog/gpu-profiling-101/

## 对我参考实现的具体改进（按性价比）

| 优先级 | 改进 | 收益 |
|---|---|---|
| ★★★ | **批量 resolve**（整帧所有 timestamp 一次 ResolveQueryData） | overhead 降到近零 |
| ★★★ | **CPU/GPU 时钟对齐做双 timeline**（`GetClockCalibration` 锚点换算到 QPC 域） | Tracy/PIX 最核心可读性 |
| ★★★ | ms 计算用 **double**（不是 UINT64 整除） | 低频 GPU 精度 |
| ★★ | **加 Pipeline Statistics query**（88B/pass，PSInvocations） | 解释 overdraw，不只说"慢" |
| ★★ | **异常 timestamp 检测**（end<begin 或 >100ms 丢弃） | 避免折线尖刺误导 |
| ★★ | 确认 **8B 对齐 + fence signal 后才 Map 读** | 防 device removal 头号原因 |
| ★★ | **PIX event 双轨标注**（DLL 形态） | 随时切 PIX 单帧深挖 |
| ★ | 折线加 **16.67ms(60fps)/8.33ms(120fps)** 参考线 + pass 按类型上色 | 从"显示数据"到"支持决策" |
| ★ | 跨 CL 比较加守卫（多 CL/async compute 时标注"仅供参考"） | 避静默错误 |
