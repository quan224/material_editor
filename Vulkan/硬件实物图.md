## 验证层 VK_LAYER_KHRONOS_validation（它是什么 + checkValidationLayerSupport 在干什么）

```
━━━━━━━ 它是什么（实物）━━━━━━━

  C:\VulkanSDK\1.4.363.0\Bin\
  │
  └─ VkLayer_khronos_validation.dll   ← 就是它！约 20MB 的 DLL，
      │                                 里面装着几百条 Vulkan 使用规则的
      │                                 检查代码（规范写明"必须这样用"，
      │                                 它逐条对着查）
      │
      └─ DLL 的元数据里登记着：
         名字 = "VK_LAYER_KHRONOS_validation"   ← 我们代码里那个字符串
                                                   就是在指名道姓要它


━━━━━━━ checkValidationLayerSupport 在干什么（两步）━━━━━━━

  第一步：问系统"你机器上装了哪些层？"
  ────────────────────────────────
  vkEnumerateInstanceLayerProperties(&count, nullptr)   ← 数几个（两段式）
  vkEnumerateInstanceLayerProperties(&count, 数组)      ← 拿名单

  枚举出来的本机层名单（= 本机装了哪些层的 DLL）：
  ┌────────────────────────────────────────┐
  │  VK_LAYER_KHRONOS_validation    ← SDK装 │
  │  VK_LAYER_LUNARG_monitor        ← SDK装 │
  │  VK_LAYER_NV_overlay            ← 驱动带 │
  └────────────────────────────────────────┘

  第二步：拿"我要的"逐个去名单里找
  ────────────────────────────────
  我要的（validationLayers 数组）：
      "VK_LAYER_KHRONOS_validation"  → 在名单里 ✓

  全找到 → return true  → 放心启用
  （假设没装 SDK：名单里没有它 → 找不到 → return false
     → create_instance 里 throw "validation layers not available"）
```

一句话：**第一步数的是本机装了哪些 DLL，第二步拿名字去对——对上才敢启用**（启用一个不存在的层，vkCreateInstance 必失败，所以先查后用）。





## CreateInfo 到底在干什么（每次 vkCreate* 的完整过程，通用机制）

```
 你这边（CPU 栈上）                驱动那边（它的内存/显存）
──────────────────────           ─────────────────────────────────

时刻 1：填表（你自己的事，没有任何人参与）
─────────────────────────────────────
VkXxxCreateInfo info{};        ← 这几行只是"在你进程的栈上
info.sType = ...;                写几十字节的内存"，
info.别的 = ...;                 loader/验证层/驱动统统不知道
                                 这张表的存在。填完放一小时也行

时刻 2：交表（vkCreateXxx 这一执行，才开始走链）─────────────
vkCreateXxx(device, &info, ..., &handle);
              ↑
              传的是指针（&info = 你栈上那块内存的地址）
   ┌─────────┴──────────────────────────────────┐
   │ loader 收到这次函数调用                        │
   │   ↓ 验证层拦截：顺着指针扫一遍表内容，查合法性    │
   │   ↓ 驱动收表："读表"就发生在这里——              │
   │      按结构体布局逐字段读你那块栈内存            │
   │      （sType 在偏移 0、下一字段在偏移 8……）     │
   │      按表施工：在驱动内部构造真身——              │
   │      一个 C++ 对象，含你填的全部配置             │
   │      + 内部状态（引用计数、绑定关系…）           │
   │      登记进对象表                              │
   └──────────────────────────────────────────────┘
   ↓ 函数返回，把新对象的编号写回 &handle（=句柄/受理号）

 之后每个调用：
 vkCmdBindPipeline(cmd, handle) ─▶ 驱动拿编号查表 → 找到真身 → 操作它
```

类比：**政府窗口**——CreateInfo 是申请表，验证层是受理窗口查材料齐不齐，驱动是后台按表建档，**句柄是受理号**，后续办事全凭受理号。"管线不可变"= 档案袋建好封死，改任何一项都要重新交表建新档。

## 显卡与队列族（第 4 章 pickPhysicalDevice / findQueueFamilies）

```
━━━ 本机有哪些卡（vkEnumeratePhysicalDevices 枚举出 2 张）━━━

 ┌────────────────────────┐   ┌────────────────────────┐
 │ Intel UHD Graphics 630 │   │ NVIDIA GeForce RTX 5060 │
 │ 核显（CPU 自带）        │   │ 主力卡：显存 8GB         │
 └────────────────────────┘   └────────────────────────┘
   两家驱动（ICD）都被 loader 装载，各报一张；
   isDeviceSuitable 两张都过 → 选先枚举到的
   （教程没打分机制；"优先独显"是可加的打分项）


━━━ 族的数据视图（vkGetPhysicalDeviceQueueFamilyProperties 查回）━━━

  族号   能力 flags（通道权限清单）          通道数 queueCount
  ─────  ──────────────────────────────────  ─────────────
   0     GRAPHICS|COMPUTE|TRANSFER|SPARSE        1   ← 全能主族
   1-8   COMPUTE|TRANSFER|SPARSE                 8   ← 纯算力族
   ...   TRANSFER 专用 / 视频编解码专用 等       …
  共 16 族（NVIDIA 消费卡典型值；精确数跑 vulkaninfo 验证）


━━━ 三个概念别混（flags ≠ queueCount ≠ 引擎）━━━

   flags     = 这条通道允许提交哪些类命令   （窗口的服务清单）
   queueCount = 这个族开放几条通道          （开了几个窗口）
   引擎      = 芯片里的物理资源             （后台的部门）

   族 0：后台所有部门都调得动（四项全能）→ 但只开 1 扇窗口；
   算力族：调不动光栅化那套电路（没有 GRAPHICS 权限）→ 开 8 扇窗


━━━ 族的芯片实物（俯视，出厂焊死：只能查、只能申请，不能造）━━━

  ┌─ GPU 芯片 ─────────────────────────────────────┐
  │ 族 0：图形引擎全套 + 1 条通道                    │
  │  ┌─ 图形引擎内部流水线 ──────────────────────┐  │
  │  │ 顶点缓冲 → ①IA 取顶点拼图元（拓扑配置）     │  │
  │  │   → ②SM 跑顶点 HLSL（可编程）              │  │
  │  │   → ③裁剪/视口单元（六比较裁剪、÷w、视口）  │  │
  │  │   → ④光栅化器（铺片元、面剔除）             │  │
  │  │   → ⑤Early-Z（着色前先测深度丢被挡的）      │  │
  │  │   → ⑥SM 跑片元 HLSL（可编程，旁挂采样器）   │  │
  │  │   → ⑦ROP（深度/模板测试、混合、写显存）     │  │
  │  └────────────────────────────────────────────┘  │
  │ 族 1-8：算力引擎（SM 阵列）×8 + 各 1 条通道       │
  │ 搬运族：DMA 引擎（拷数据，不画画）                │
  │ 编码族：视频编解码专用单元                        │
  └──────────────────────────────────────────────────┘
   第 11 章的八张表 = 给 ①③④⑦ 这些固定电路逐个下配置

  ── ⑦ROP 详解（Render Output Unit，渲染输出单元）──
     管线最后一个硬件单元：片元着色器算完颜色，活交给它——
     负责把颜色安全地写进帧缓冲。三件事对应两张表：

       深度/模板测试（被挡的丢）   ← VkPipelineDepthStencilState（现在 nullptr）
       颜色混合（新旧按公式合并）  ← VkPipelineColorBlendState（伪代码那段）
       写入（colorWriteMask 选通道）← 同上表

     现配置（blendEnable=false、无深度）下干最原始的活：直通——
     着色器给什么写什么。名字来历：老术语 Raster OPeration，
     D3D 时代把混合+写回这级叫"光栅操作阶段"。
     物理位置在 die 边缘贴显存控制器（工作就是写显存，住门口）。

  ── ②⑥ SM 详解（Streaming Multiprocessor，流式多处理器）──
     SM = 跑 HLSL 的小格子，一个"微缩处理器"——取指令、执行、
     有自己的寄存器/缓存/调度器，能独立跑完整的着色器程序。

     内部：128 个着色器核心（分 4 组）+ 寄存器文件（着色器变量/
     属性槽的硬件实体）+ L1 缓存 + 纹理采样器 + 4 个 warp 调度器。
     调度单位是 warp（32 线程一束）：一个 SM 同时驻留约 2000 线程，
     谁的数据没到就让位给别的束，靠轮换保持核心不停工。

     为什么一个芯片要几十个 SM：
       ① 图形负载天然海量并行——800×600 就有 48 万个像素，
          每个像素独立跑同一段片元着色器，任务天然拆得粉碎，
          多少个 SM 都喂得饱
       ② 用线程切换隐藏延迟——显存读一次要几百个时钟周期，
          CPU 靠大缓存等待；GPU 靠"等数据的束让位、就绪的束顶上"，
          核心数越多、驻留线程越多，越能保持满载。哲学：
          CPU 是少量快核心追低延迟，GPU 是海量简单核心追吞吐

     数量：消费卡几十个（总核心数 = SM 数 × 128，宣传页的
     "CUDA cores" 就是这个乘积）。5060 精确数查官网规格页
     或 CUDA deviceQuery——不编。所有 SM 是公共池，
     图形族/算力族共用，驱动调度器派活。
```

```
━━━ 队列句柄拿到后怎么用 + 队列的职责边界 ━━━

 每帧两个动作（第 15/16 章登场）：
   vkQueueSubmit(graphicsQueue, ..., &submitInfo, fence)  ← 录好的命令缓冲排进队列（画）
   vkQueuePresentKHR(presentQueue, &presentInfo)           ← 画好的图像排进队列（上屏）

 本机 graphicsQueue == presentQueue（同族同条 → 同一个值，两个别名）。
 不会"覆盖"——队列是排队结构（FIFO）：每次提交都是追加到队尾，
 同队列先提交先执行：
   [画1帧][上屏1帧][画2帧][上屏2帧]... —— 先画完才轮到上屏，顺序天然安全
 别的卡若两族不同：两条独立队列并行、顺序无保证，要信号量同步
 （教程的 imageAvailable/renderFinished 即为此，通用写法）。

 ── 队列不管"去哪个硬件单元"── 职责分工：

   队列决定：入口（命令从这条通道进，族 0=允许收画类命令）
             + 顺序（同队列先提交先执行）——仅此两件
   命令缓冲内容决定"做什么"：vkCmdDraw=画、vkCmdCopyBuffer=搬运
                             （命令类型就是任务单）
   管线决定"怎么画"：烘焙的拓扑/光栅化/混合配置（第 11 章八张表）
   GPU 调度器派活：命令处理器读命令 → 按类型分发——
                   draw 派 SM→光栅→ROP 全链，copy 直派 DMA
                   （去哪个"窗口"是它的事，不是队列的）

 类比：队列=传送带入口；命令缓冲=订单；管线=配方书；
       调度器=后厨主管（拆单派工）。申请队列=占工位，
       订单和配方是你另外准备的，派工是后厨自己的事。
```
